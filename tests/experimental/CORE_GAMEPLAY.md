## 3. Authoritative update order and core dependency map

Current `simulation/simulation.gd:update` orders each offline tick as follows:

1. Capture starting Heat and reconcile offline/realm interval bookkeeping.
2. Apply automatic upgrades in registry order; resolve their unlock/modifier/threshold effects.
3. Compute the Eternal Furnace multiplier once.
4. Visit generators in registration order: **Atomic Friction → Molecular Agitation → Lava Mites → Condensation → Matter Furnace → Arcane Compressor → Forge → Relic Crucible**.
5. Update a generator's throttle controller before its operating check. Continuous generators start if eligible; cap duration by available input/rate. **Consume inputs, then calculate/produce outputs using the mutated state.** Later generators see earlier transactions. Partial intervals can end with operating false.
6. Apply Matter decay, recording lost Matter and converting the same amount into produced Heat.
7. Apply Heat leak, using post-production/post-decay and tick-start Heat. The stiff branch uses the existing implicit substep Heat-balance integrator.
8. Run generator autobuyers in their existing order, then upgrade autobuyers in their tree/registry order.
9. Complete offline-entry/log bookkeeping. No active-play economy snapshots are generated during offline catch-up.

Threshold joins, sensitivity changes and environmental feedback are usually nonlinear **continuous** behavior. Integer output, purchase, unlock, throttle/operating changes and cycle completion are discrete. The diagnostic `input_enclosure`/`changing_rate_dependency` categories mean the current experiment lacks a proof; they do not assert that every consumer or nonlinear modifier is inherently discontinuous.

## 4. All-blocker instrumentation and controlled ablations

`core_blockers.gd` enumerates simultaneous capability restrictions instead of returning at the first guard failure. It derives changing resources from active IO and environmental conversion, inspects relevant input/output/speed modifiers and sensitivities, records automatic-resource event exposure and asks the existing automation boundary checker for its current proof status. Every detail names the affected generator/resource/subsystem. In these fixtures there is one enabled generator autobuyer, so a first enabled-tree automation status does not hide a second active buyer. The existing full suite retains multi-buyer ordering tests.

`core_investigation_runner.gd` records category counts, generator/resource details, co-occurrence combinations and sole-category counts. Sampling occurs at guard calls; with these all-exact 120-second runs, there are 120 one-second fallback windows. A count of 120 therefore represents **120 guard windows / 120 seconds attributed at that resolution**, not proof that a condition held at every interior microstep. The exact activity survey separately observes every reference tick. Overlapping counts must not be summed as disjoint lost simulation time. Diagnostic microseconds and wall times are excluded from throughput medians.

The categories are conservative obligations, not all independent physical causes. `inactive_consumer_guard` is frequently an overconservative controller-state exclusion; growing affordability and clock dependencies also need proofs rather than necessarily occurring events. Genuine production/output/operating events and actual environmental activity are measured separately. Unknown bounds remain unknown; the survey does not bypass them.

## 5. Forge cycle boundary investigation

The Normal Forge has real activation cost/scaling, per-operating-time Heat and Matter inputs, continuous Ash output, and a completion CF reward. Careful, Fast and Infernal modes have different durations, inputs, outputs, production/activation multipliers and unlock upgrades. This investigation does not rename, unlock or retune them to simplify a fixture.

The actual offline path in `Simulation.update_cycle_generator`:

1. An inactive cycle starts only through a successful activation purchase, or legitimately unlocked auto-run. It deducts real cost/crafting inputs, applies the configured level increment, captures the crafting critical snapshot and marks the cycle active.
2. A stopped cycle must pass its operating check. Offline code computes time remaining from duration/progress and the **current** speed multiplier, caps requested elapsed time and then caps it again by available inputs.
3. Inputs are consumed and regular outputs are produced in their original order. Only then is `_get_cycle_progress_delta` called, which **re-evaluates speed**. Ash created by the Forge can therefore affect the progress awarded for that same step. Starting-speed extrapolation is not the reference update map.
4. Completion compares progress against duration minus the existing `0.000001` tolerance. Completion runs through `complete_cycle`, not a separate experimental reward calculator.
5. Event-trigger effects are visited in their existing order. Effective chances include live upgrade/relic modifiers and sensitivities. A probability of one short-circuits without an RNG sample; intermediate chances use the owned gameplay RNG. Completion consequences preserve their event ordering and any level reduction.
6. Completion outputs, critical multipliers, inventory/shard/random-relic rewards and signals execute through their real paths. CF completion also removes remaining Heat and records its loss. Cycle flags/progress and critical snapshots are cleared. The offline auto-run loop can pay for a new activation and use remaining time within the same reference tick.

Forge critical event chances are evaluated live at completion; the generic cycle critical snapshot is used by relic crafting's random-tier reward path, not a blanket replacement for Forge event chances. Equipment locking limits swaps but does not freeze held-resource sensitivities, automatic upgrades or production changes. Upgrades, modes, level changes, realm parameters and relevant relic modifiers all require invalidation of a speed/configuration proof. These fixtures do not grant unearned critical upgrades or auto-run technology. The retained first-cycle witness produces the ordinary reward; it is not evidence that a new hybrid RNG implementation has been validated. No such implementation was enabled.

### A conditional boundary is possible

`core_cycle_bound.gd` investigates a generic formula capability, with **no generator-ID or fixture recognition in a scheduler**. For fixed cycle/mode/modifier/sensitivity/realm parameters and nonnegative resource domains:

- The existing nonnegative inverse-sqrt penalty has raw multiplier in `[0, 1]`, even as its resource changes.
- Static sensitivities, and supported dynamic inverse-sqrt sensitivities with nonnegative coefficients, provide sensitivity intervals.
- The helper bounds the corners of `1 + (raw - 1) * sensitivity`; absolute factor bounds safely cover signs when sensitivity exceeds one and individual factors become negative. Their product bounds the final nonnegative-clamped cycle speed. Known static/generator-level and bounded exponent cases are supported conditionally; unknown/unbounded formulas return unknown.
- Given an upper speed `S`, remaining progress `R`, and the actual completion comparison tolerance, completion cannot occur earlier than approximately `(R - tolerance)/S`. A small outward numerical margin is retained. Input starvation can delay completion, so ignoring it here makes the lower time bound earlier, not later.

For the reached Normal Forge, the conditional speed ceiling is 1.0 and its initial conditional lower time is about 599.999999 seconds. This is **not** a constant-Ash/current-speed forecast. Observed speeds in the mature activity cases vary substantially. The helper defaults to `unknown` without an explicit frozen-configuration assumption; the caller passing `true` is an assumption for research probes, not an automatically established production invariant. Its nonnegative-domain and fixed-configuration assumptions must be proved by a future envelope provider. It is never called to skip simulation ticks.

A completion lower bound only excludes one event type. It does not prove that Condensation's next integer output, an input clamp, a throttle transition, an automatic upgrade or an affordable purchase lies outside the interval. A cycle-only exception would therefore remain unsafe or useless in these fixtures.

## 6. Hybrid architecture assessment and decision

The architecture is currently a **guarded smooth-subset integrator**, not a general hybrid simulator. Its guards are an essential part of its correctness contract:

- `continuous_checkpoint.gd` captures amounts, operating/throttle flags, statistics, discovery, environmental reward totals, dormancy and selected log bookkeeping. It omits cycle progress/active state, discrete-production remainders, purchased levels/effects, automation mutations, RNG, inventories, gameplay events and emitted signals.
- `adaptive_metrics.gd` observes cycle progress numerically, but `feedback_offline.gd:_map_advance` writes back only resources, statistical fields, environmental reward accumulators and dormancy. Adding a numeric metric or a checkpoint field does **not** make the map operator integrate a cycle clock or an output phase correctly.
- Predictor probes run actual Simulation updates at extrapolated resource states. A probe can cross an unlock, integer output, purchase or completion that the intended trajectory would not. The current response to an unexpected discrete signature/RNG change is a strict failure requiring the experimental state to be discarded, not a complete transactional rollback followed by an authoritative boundary tick.
- Step doubling estimates resource/statistical error; it does not enclose the true repeated 0.1-second trajectory or certify the first affordable/floor/completion tick. Correct final amounts cannot prove correct purchase priority, intervening Matter boosts, integer output timing or later RNG.

The dense tests make the checkpoint limitations concrete using **copies of real reached states**. Restoring the restricted checkpoint after the real Forge completion does not restore its active flag/progress. Restoring it after one early-game update does not restore Condensation's fractional output remainder. These are expected out-of-contract cases, not production bugs; existing guards prevent them from being attempted in production or in accepted experimental intervals.

**Decision after fixtures and ablations:** do not add another guard exception. No single observed guard category is the sole restriction in any primary sampled window. Removing cycles or automation, including both together, unlocks no core adaptive time. Admitting cycles would still leave recurring discrete output, coupled inputs, stateful allocation, resource-sensitive rates and potentially affordable automation. A complete safe extension would cross several interfaces; none was justified as a small, validated change in this assignment. The conditional boundary helper and diagnostics are research deliverables, not a claimed optimization.

### Minimal concrete next implementation

No production rewrite or large event queue is required for the first engineering step. Keep a new experimental adapter with three explicit contracts:

1. **Transactional trial state.** Run trial probes in an isolated Simulation/seeded GameState, or implement a complete experimental checkpoint. Include cycle flags/progress, output remainders, levels/effects, all automation state, owned RNG, relic/inventory state, resource/statistical/reward state and relevant simulation indexes/caches. Buffer event logs/signals until commit; discard rejected probes without exposing callbacks. Begin with tests that reject immediately before and after an actual purchase, integer output and cycle completion and prove complete restoration. SaveManager alone is insufficient: its normal-load behavior intentionally omits transient flags and is not a drop-in live checkpoint.
2. **Typed continuous state vector.** Explicitly describe writable resources, cycle clocks, output phases and statistics. The map operator must advance/apply every approved component. Discrete fields remain authoritative transactions. Do not repurpose observational metric-string keys as the integration API.
3. **Shared event/resource envelope.** Return a conservative reference-grid `safe_until`, resource box and unresolved obligations from IO, modifier, sensitivity, controller and environmental contracts. Recompute after purchases/unlocks/mode/completion changes. Any unknown obligation takes one exact tick. Candidate and endpoint probes need the same enclosing proof. Execute the boundary tick through the original ordered Simulation update and RNG; do not implement another completion/purchase calculator.

This foundation alone promises **no speedup**. The next numerical target should be a bounded deterministic IO batch for Condensation plus downstream consumers on the original tick grid. Matter units can change downstream inputs and future Heat immediately, so preserving only a batch's final whole-unit total is insufficient. The measured high integer-output density below means a scheduler that merely stops before every output may have almost no useful step width. Use that evidence to compare a certified reference-map batch against a more efficient exact tick kernel, rather than committing to a general event scheduler in advance. No new gameplay setting or save field is needed.

## 8. Accuracy, regression and compatibility

**88 full regression groups passed, 0 failed.** The focused investigation suite passed **6,000 reference-grid endpoints** across five mature states, three windows immediately before/at/after the reached first Forge completion, instrumentation-observational checks, read-only conditional-bound checks, formula-domain Ash probes and the restricted-checkpoint scope tests. The first completion after loading its real witness occurs at reference tick **1**; no fabricated progress value is used. The 6,000 dense sample pairs also include the windows around actual Thermic Mass activation at tick 27, Mite unlock at tick 439 and the charging-control AF autobuyer purchase at tick 985, with exact event logs and the adjacent endpoints compared.

Discrete signatures include levels, modes/output unlocks, operating/throttle/cycle flags, fractional output state, discoveries, automation waiting/cooldown dictionaries, purchases and their tick/cost ordering, inventories/relics, rewards and gameplay event history. Gameplay RNG is compared exactly.
